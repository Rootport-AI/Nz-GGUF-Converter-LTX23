# K量子化カーネル（Q4_K / Q5_K / Q6_K）実装メモ

このドキュメントは、`src/converter/quant_kernels.py` に実装した K系量子化
（K-quant）の書き込み側カーネルについて、移植元・データ配置・C実装との対応・
検証結果・既知の制限をまとめたものです。

## 1. 概要と背景

GGUF を扱う Python ライブラリ `gguf-py`（本プロジェクトが依存している `gguf`
パッケージ）は、Q4_K / Q5_K / Q6_K の「復元（dequantize、読み出し）」だけを実装
しており、「量子化（quantize、書き込み）」は未実装です。そこで llama.cpp の
C 参照実装を NumPy へ忠実に移植しました。

- 移植元リポジトリ: ggml-org/llama.cpp（master ブランチ）
- 移植元ファイル: `ggml/src/ggml-quants.c` および構造体定義 `ggml/src/ggml-common.h`
- 取得方法: GitHub の raw URL から取得
  （`https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-quants.c`）
- 取得・移植日: 2026-07-10（llama.cpp master 時点）
- 移植した関数:
  - `quantize_row_q4_K_ref`（補助関数 `make_qkx2_quants`、6ビットスケールのパッキング）
  - `quantize_row_q5_K_ref`（同上の5ビット版）
  - `quantize_row_q6_K_ref`（補助関数 `make_qx_quants`）
- 重要度行列（imatrix、importance matrix。各要素の重みづけに使う行列）は使わない
  参照版（imatrix-free ref）として移植しています。

## 2. 公開API

`src/converter/quant_kernels.py`

- `quantize_q4_k(arr) -> np.ndarray(uint8)`
- `quantize_q5_k(arr) -> np.ndarray(uint8)`
- `quantize_q6_k(arr) -> np.ndarray(uint8)`
- `quantize(arr, ggml_type_name)` … `"Q4_K"` / `"Q5_K"` / `"Q6_K"` を文字列で
  指定してディスパッチする関数

入力は float32 の NumPy 配列（任意次元、C連続）です。ggml と同じく最終軸（メモリ
上で連続する方向）を行として、256要素ごとの「スーパーブロック」に分割して量子化
します。要素総数が256で割り切れることを `assert` で確認します（割り切れないテンソル
は typemap 側で非量子化に割り当て済みのため、ここへは来ません）。出力は GGUF に
そのまま書き込めるバイト列（uint8 配列）で、形状は「最終軸をバイト長に置き換えた
もの」になります。

## 3. ブロックのバイト配置（レイアウト）

256要素あたりのバイト数（`type_size`）は、`gguf` の `GGML_QUANT_SIZES` および
`ggml-common.h` の構造体と厳密に一致させています。

### Q4_K … 144バイト / 256要素

```
オフセット  サイズ  内容
0           2       d      … スケール用スーパーブロック係数（float16）
2           2       dmin   … 最小値用スーパーブロック係数（float16）
4           12      scales … 8個のサブブロックのスケールと最小値を6ビットで詰めたもの
16          128     qs     … 4ビット量子（256個）
```

### Q5_K … 176バイト / 256要素

```
オフセット  サイズ  内容
0           2       d      … スケール用係数（float16）
2           2       dmin   … 最小値用係数（float16）
4           12      scales … 6ビットのスケール・最小値
16          32      qh     … 各量子の最上位ビット（5ビット目）
48          128     qs     … 各量子の下位4ビット
```

### Q6_K … 210バイト / 256要素

```
オフセット  サイズ  内容
0           128     ql     … 各量子の下位4ビット
128         64      qh     … 各量子の上位2ビット
192         16      scales … 16個のサブブロックのスケール（int8、符号あり8ビット）
208         2       d      … スーパーブロック係数（float16）
```

いずれも `gguf.quants` の `dequantize_blocks` が期待する配置と厳密一致しており、
`gguf.quants.dequantize` が例外なく読めること自体がレイアウト検証になっています。

### サブブロック構成

- Q4_K / Q5_K: 256要素を32要素ずつ8個のサブブロックに分割し、各サブブロックごとに
  スケール（`scale`）と最小値（`min`）を `make_qkx2_quants` で最適化します。8個の
  スケール・最小値をスーパーブロック全体で正規化し、6ビット×2（スケール・最小値）
  にまとめて `scales`（12バイト）へパックします。
- Q6_K: 256要素を16要素ずつ16個のサブブロックに分割し、各サブブロックのスケールを
  `make_qx_quants` で最適化します。こちらは最小値を持たない対称量子化です。

## 4. C実装との対応表

| C（ggml-quants.c）                | 本実装（quant_kernels.py）           | 備考 |
|-----------------------------------|--------------------------------------|------|
| `nearest_int`                     | `_nearest_int`                        | 「マジックナンバー」加算による四捨五入（最近接偶数丸め）をビット演算で再現 |
| 逐次的な浮動小数の総和            | `_fsum`（`np.cumsum` で実装）         | 最終軸に沿った float32 の逐次加算。C の累積順序をビット単位で再現するため |
| `GGML_FP32_TO_FP16`               | `astype(np.float16)`                  | 最近接偶数丸め。NumPy と ggml 参照実装で一致 |
| `make_qkx2_quants`（use_mad=false）| `_make_qkx2`                          | Q4_K / Q5_K のスケール・最小値探索 |
| `make_qx_quants`（rmse_type=1）   | `_make_qx`                            | Q6_K のスケール探索（重み=x²、-9..9のスケール掃引） |
| `get_scale_min_k4` の逆操作       | `_pack_scales_6bit`                   | 6ビットスケール・最小値のパッキング |
| `quantize_row_q4_K_ref`           | `_quantize_q4_k_blocks`               | |
| `quantize_row_q5_K_ref`           | `_quantize_q5_k_blocks`               | qh の最上位ビットの詰め方を含む |
| `quantize_row_q6_K_ref`           | `_quantize_q6_k_blocks`               | ql/qh の詰め方を含む |

### 浮動小数演算の忠実性について

C 実装は `float`（32ビット）で計算し、`-ffast-math` を使わないため加算の順序を
入れ替えません。したがって総和は逐次加算になります。NumPy の `sum` は8個の
アキュムレータを使う展開加算で、C の逐次順序と最終ビットで食い違うことがあり、
`nearest_int` の境界（ちょうど中間の値）で丸め結果が反転してブロック不一致を
生む可能性があります。これを避けるため、探索に効く総和はすべて `_fsum` で
逐次加算しています。実装は Python ループではなく `np.cumsum`（float32、最終軸）
の末尾要素を使います。cumsum は左から右へ float32 で逐次加算し各部分和を float32 に
丸めるため、素朴なループ累積とビット単位で一致しつつ、C呼び出し1回で済み高速です。
すべての演算は float32 を維持し、不要な float64 への昇格を
避けています（NumPy 2.x の NEP50 により Python の float リテラルは float32 配列を
昇格させませんが、念のためスカラは `np.float32(...)` で明示しています）。

## 5. 検証結果

参照GGUF: `LTX-2.3-22B-distilled-1.1-Q4_K_M.gguf`
（Q4_K=1242個、Q5_K=68個、Q6_K=322個のテンソルを含む）

### 5-1. 移植の忠実性ゲート（参照モデル不要・最重要）

`make_qkx2_quants` / `make_qx_quants` を「C の演算順序をそのまま写した純スカラ版」
として別実装し、ベクトル化カーネルと**ビット単位で一致するか**を乱数データで比較
します（`tests/test_quant_roundtrip.py` の `test_fidelity_make_qkx2` /
`test_fidelity_make_qx`）。

- 結果: 乱数サブブロック各400個で **不一致ゼロ（ビット完全一致）**。
- さらに実データのサブブロック各2000個でも scale・min・L すべて不一致ゼロを確認済み。

これにより、ベクトル化した実装が C の参照アルゴリズムを浮動小数の丸めまで含めて
正確に再現していることが保証されます。

### 5-2. べき等テスト（実テンソルの再量子化）

参照GGUF の実テンソルを `gguf.quants.dequantize` で float32 に復元し、自作カーネル
で再量子化して、**元の生バイトとの一致率**を測ります。サイズを大小取り混ぜて各タイプ
40テンソルを抽出した集計は以下のとおりです。

| タイプ | ブロック一致率 | 完全一致テンソル | 再量子化SQNR |
|--------|----------------|------------------|--------------|
| Q4_K   | 99.90%         | 40中6            | 69.3 dB      |
| Q5_K   | 85.50%         | 40中0            | 46.6 dB      |
| Q6_K   | 85.67%         | 40中0            | 72.7 dB      |

不一致は `scales` 領域に集中しており（そこから連鎖して qs/qh も変わる）、d・dmin は
ほぼ完全一致です。不一致ブロックでもバイト一致率自体は97〜99%と高く、差は「量子
レベルが1つずれる」程度の小さなものです。

**なぜ100%にならないか（原因分析）**

これは移植の不具合ではなく、K量子化アルゴリズムの本質的な性質です。上記5-1の
とおりカーネルは C 参照実装とビット単位で一致しているため、探索ヒューリスティック
（`make_qkx2_quants` の rmin/rdelta/nstep の掃引や丸め）に差分はありません。

べき等にならない理由は、スケール探索が「元の float32」ではなく「一度復元された
float32（fp16丸めされた d と6ビット化されたスケールで再構成した値）」に対して
再最適化するためです。復元後の値は元の値と厳密には異なるので、重みづき最小二乗の
探索が、別の（しかし同等に妥当な）局所最適へ着地するブロックが一定割合で生じます。

- Q4_K は探索が安定しており、ほぼべき等（99.9%）になります。
- Q5_K / Q6_K はより細かい量子格子（nmax=31 / 32）で、復元値が再最適化の境界近くに
  乗りやすく、一致率は85%前後になります。
- さらに、参照モデルが重要度行列（imatrix）付きで量子化されている場合、元のスケール
  はそもそも imatrix-free の探索が導く値と異なるため、べき等率はより下がります
  （本移植は仕様どおり imatrix なしのため、この差は想定内です）。

**品質評価**

不一致ブロックでも再構成誤差は小さく、Q6_K の再量子化SQNRは72.7 dB と非常に高い
です。Q5_K の再量子化SQNR（46.6 dB）が相対的に低いのは、最小値を引く非対称量子化
のため、別の最適解に着地したときの誤差が対称量子化より大きく出やすいことによる
もので、カーネルの不具合ではありません（下記5-4の素の量子化品質を参照）。

### 5-3. ラウンドトリップ統計（乱数・実データ）

乱数データ（正規分布・一様分布・外れ値入り）と実データで quantize→dequantize を
行い、バイト長が正しいこと、`gguf.quants.dequantize` が例外なく読めること、
再構成誤差（最大絶対誤差 / RMSE / SQNR）を確認します。全ケースで有限値かつ
レイアウト整合を確認済みです。

### 5-4. 素の量子化品質（ビット数と誤差の整合）

新規の乱数データ（正規分布、256×4096）を1回だけ量子化→復元した際の SQNR:

| タイプ | SQNR    | 最大絶対誤差 | RMSE   |
|--------|---------|--------------|--------|
| Q4_K   | 22.9 dB | 0.304        | 0.0714 |
| Q5_K   | 28.8 dB | 0.142        | 0.0361 |
| Q6_K   | 35.0 dB | 0.0774       | 0.0177 |

1ビット増えるごとに約6 dB 改善しており（量子化理論どおり）、Q5_K は Q4_K より、
Q6_K は Q5_K より確実に高精度です。カーネルが正しく動作していることの裏づけです。

### 5-5. スループット（実測）

4096×4096（64 MiB の float32 入力）を量子化した実測速度と、22Bモデル全体
（量子化対象およそ15 GB 分の float32 入力）の予想処理時間の一例（CPU依存）:

| タイプ | 実測速度   | 15 GiB分の予想時間 |
|--------|------------|--------------------|
| Q4_K   | 約6.7 MiB/s | 約38分             |
| Q5_K   | 約8.4 MiB/s | 約30分             |
| Q6_K   | 約12.3 MiB/s | 約21分            |

スーパーブロック軸で完全にベクトル化しており、Python ループは探索の固定ステップ数
（Q4_K は21回、Q5_K は16回、Q6_K は18回のスケール掃引）のみです（逐次総和は
`np.cumsum` を用いた C 呼び出しに置き換え済み）。速度は 1回限りのオフライン変換
として十分実用的です。数値は環境依存のため、`test_throughput`（`-s` 付き実行）で
各自の環境の実測値を確認できます。

## 6. 既知の制限

- 重要度行列（imatrix）には非対応です（仕様どおり imatrix なしの参照版）。imatrix
  付きで量子化された参照モデルに対しては、べき等率が下がります。
- llama.cpp の SIMD 最適化経路ではなく、`quantize_row_*_K_ref`（参照実装）を移植して
  います。参照実装と最適化実装は結果が一致する設計ですが、本移植の基準はあくまで
  参照実装です。
- 逐次総和による忠実性を優先しているため、探索部分は純粋な `np.sum` を使う場合より
  やや遅くなります（その代わりビット単位の再現性が得られます）。
- fp16 変換は NumPy の `astype(np.float16)` に依存します。正規化数の範囲では ggml の
  参照変換と一致しますが、非正規化数などの極端な端では理論上の差が残り得ます
  （スケール係数は正の正規化数域のため実害はありません）。
